# 计费分析页面需求文档

## 背景

现有数据看板里的“请求次数”“统计次数”与使用日志里的调用记录不是稳定的包含关系，容易造成误解；这些指标已经从数据看板移除。后续计费相关统计应以使用日志为事实源，新增一个专门页面承载“额度、Tokens、订阅、余额、令牌、模型、用户”等分析。

## 目标

新增“计费分析”页面，用于回答：

1. 指定时间范围内一共消耗了多少额度、多少日志 Tokens、多少次消费记录。
2. 这些额度中有多少来自余额消耗，有多少来自订阅抵扣。
3. 每个令牌、模型、分组、渠道、用户分别用了多少 Tokens 和额度。
4. 不同倍率、模型价格、订阅抵扣带来的结果不以单一“倍率”误导展示，而用有效单价和明细入口表达。

## 非目标

1. 不替代使用日志的逐条审计能力。
2. 不在第一版里重做完整利润报表、供应商成本或财务结算。
3. 不继续使用 `quota_data` 作为计费分析事实源；该表可用于历史趋势图，但不用于本页面的精确计费拆分。

## 数据口径

第一版计费分析以 `logs` 表中的消费日志为统计源：

1. 只统计 `type = LogTypeConsume` 的消费日志。
2. “请求数”在本页面内明确为“消费日志数”，即本时间范围内消费日志记录条数。
3. “日志 Tokens”按 `prompt_tokens + completion_tokens` 计算。图片、任务、音频、固定价格等非标准 token 计费场景可能没有完整 token 表达，因此页面命名必须避免写成“总 Tokens”。
4. `Other.billing_source = "subscription"` 时计入“订阅抵扣”；优先使用 `Other.subscription_consumed`，为空或小于等于 0 时回退到日志 `quota`。
5. 非订阅来源计入“余额消耗”，金额使用日志 `quota`。
6. “总消耗额度”按“余额消耗 + 订阅抵扣”计算，保证拆分项可以对齐总数。
7. 退款、失败、系统日志、充值日志不进入第一版消费分析；后续可新增“退款抵扣 / 净消耗”口径。

## 普通用户视图

普通用户只能看到自己的数据：

1. 汇总卡片：总消耗额度、余额消耗、订阅抵扣、日志 Tokens、消费日志数、有效单价。
2. 维度表：令牌、模型、分组。
3. 每行展示：消费日志数、日志 Tokens、总消耗、余额消耗、订阅抵扣、每 1K token 有效额度、最近使用时间。
4. 不展示其他用户、渠道、全站汇总或平台成本信息。

## 管理员视图

管理员可以看到全站或筛选后的数据：

1. 汇总卡片同普通用户。
2. 额外维度表：用户、渠道。
3. 支持按用户名、令牌名、模型名、渠道 ID、分组、时间范围筛选。
4. 管理员看到的是运营分析，不替代逐条日志审计；需要定位明细时仍回到使用日志。

## 前端入口

1. 在控制台侧边栏新增“计费分析”。
2. 路由：`/console/billing-analysis`。
3. 页面首屏直接展示分析结果，不做营销页或说明页。
4. 统计卡片和表格必须在移动端和桌面端都可用，长模型名、令牌名要省略显示并保留 tooltip。

## 后端接口

新增接口：

1. `GET /api/billing/analysis/self`：普通用户自己的计费分析。
2. `GET /api/billing/analysis`：管理员计费分析。

查询参数：

1. `start_timestamp`
2. `end_timestamp`
3. `username`（仅管理员）
4. `token_name`
5. `model_name`
6. `channel`
7. `group`

返回结构：

1. `summary`
2. `users`
3. `tokens`
4. `models`
5. `channels`
6. `groups`

普通用户接口不返回 `users` 和 `channels`。

## 验收标准

1. 后端测试覆盖余额消费、订阅抵扣、筛选、普通用户维度限制。
2. 前端新增页面能在当前 dev 环境打开。
3. 普通用户看不到用户、渠道维度。
4. 管理员可以筛选用户名、令牌、模型、渠道和分组。
5. `bun run build` 通过。
6. 不修改无关页面，不触碰已有未关联用户改动。
